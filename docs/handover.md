# 納品・本番公開手順

## 方針と状態

開発中は制作者自身の環境で構築・確認します。納品時にクライアントにCloudflareアカウントを作成してもらい、クライアントのアカウント内に本番サイトをデプロイします。

本書は手順のたたき台です。起動確認用の環境は構築済みです。各ページとCMS接続の実装後に設定項目を見直し、実際の公開作業で検証します。アカウント作成・外部設定はまだ行っていません。

## 1. 納品前に決めること

| 対象 | 方針・確認事項 |
| --- | --- |
| Cloudflare | 本番はクライアント所有。クライアント自身がアカウントを作成 |
| GitHub | リポジトリの最終所有者、Pagesからの読み取り権限、納品後のコード管理者を決める |
| microCMS | サービスの最終所有者、管理者、編集者、開発用データの扱いを決める |
| ドメイン | 所有者、DNS管理先、更新費用の負担者、既存メールの有無を確認 |
| 保守 | 更新対応、障害連絡先、制作者のアクセスを残す範囲・期間を決める |

Cloudflareだけを切り替えても、GitHubやmicroCMSが制作者に依存していれば運用の引き継ぎは完了しません。
CMSを別サービスへ作り直す場合は、スキーマ、原稿、画像、コンテンツIDと記事URLの対応を確認します。具体的な移行方法は所有方針の確定後に追記します。

## 2. クライアントによる準備

1. クライアントが自分で管理できるメールアドレスでCloudflareアカウントを作成する。
2. 多要素認証を設定し、復旧方法をクライアント自身で保管する。
3. 制作者が設定を代行する場合は、必要な操作ができる権限で招待する。パスワードを共有しない。
4. GitHub・microCMS・ドメインの管理権限と、公開予定日を確認する。

## 3. 本番用Pagesプロジェクトを作成

1. クライアントのCloudflareアカウントで、Git連携方式のPagesプロジェクトを新規作成する。
2. 合意したGitHubリポジトリへの連携を承認し、本番用ブランチを指定する。
3. ビルド設定を登録する。現時点の想定はAstro SSG、出力先 `dist`。ビルドコマンドは `pnpm build`。
4. Node.js 26.13.0、pnpm 11.6.0、`pnpm-lock.yaml` を使用する。
5. 本番用の環境変数を設定する。

| 変数 | 本番で設定する値 |
| --- | --- |
| MICROCMS_SERVICE_DOMAIN | 本番用microCMSサービスの識別子 |
| MICROCMS_API_KEY | 本番用の読み取りAPIキー |
| SITE_URL | 最終公開URL。独自ドメインがある場合はそのURL |

秘密の値はこの手順書やリポジトリに記載しません。プレビュー環境を使用する場合は、本番とは別に設定・確認します。

Git連携の設定方法は[Cloudflare公式ガイド](https://developers.cloudflare.com/pages/get-started/git-integration/)を参照します。

## 4. 仮URLで確認

1. 本番側でビルドを実行し、Pagesの仮URLで表示を確認する。
2. 記事一覧・詳細・写真・プロフィール・404・スマートフォン表示を確認する。
3. 本番データ、画像、連絡先が正しく、サンプルや開発用リンクが残っていないことを確認する。
4. 最終公開URLを `SITE_URL` に設定した状態で、canonical・OGPに開発URLが残っていないことを確認する。
5. ビルド失敗時のログの見方と再実行方法をクライアントに案内する。

## 5. CMSの自動更新を接続

1. クライアント側のPagesプロジェクトで、本番ブランチ向けのDeploy Hookを新規発行する。
2. microCMSのWebhook送信先を本番側のHookに設定する。開発側のHook URLを流用しない。
3. 4 APIそれぞれの公開・更新・公開停止・削除で、本番ビルドが起動することを確認する。
4. 下書き保存で不要なビルドが起動しないことを確認する。
5. 合意したテスト用コンテンツで、編集から公開サイトへの反映までクライアントと一緒に確認する。

送信成功だけでなく、ビルド成功と画面への反映まで確認します。Hook URLは秘密として扱います。
設定は[Deploy Hooksの公式ガイド](https://developers.cloudflare.com/pages/configuration/deploy-hooks/)を参照します。

## 6. 独自ドメインで公開

1. ドメインとDNSの管理者に変更内容・作業日時を確認し、承認を得る。
2. 既存サイトがある場合は、現在のDNS設定と復旧方法を控える。メール用のMX・TXTなど、サイト以外の既存設定も確認する。
3. Pagesのカスタムドメイン設定から登録し、案内に従ってDNSを設定する。
4. HTTPS、ドメインの応答、ページ・画像・リンク、CMS更新を確認する。
5. 問題がある場合はDNSを変更前に戻すなど、事前に決めた方法で復旧する。

ルートドメインでの利用とサブドメインでの利用ではDNSの条件が異なります。ネームサーバー変更を一律の手順にせず、[カスタムドメインの公式ガイド](https://developers.cloudflare.com/pages/configuration/custom-domains/)と実際の管理状況を確認します。

## 7. 引き継ぎと開発環境の整理

- クライアントがPagesの公開状況・ビルドログを確認できる。
- クライアントがmicroCMSで更新し、本番反映を確認できる。
- ソースコード、CMSフィールド定義、ビルド設定、ドメイン情報、障害連絡先を引き渡す。
- パッケージ・Node.jsの確定バージョン、公開したコミット、検証日を記録する。
- 開発用Webhookを無効化し、不要な開発サイトは合意後に停止する。本番確認前には削除しない。
- 保守契約に応じて制作者の権限を整理し、不要なキーは失効・更新する。
- 納品資料に秘密の値を残さず、必要な情報は合意した安全な方法で引き渡す。
